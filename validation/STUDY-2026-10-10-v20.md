Branch `v20/qwen35-122b` (off `v19/flashnext`, local only). Rig tree `/opt/llamacpp/tmp-v20` (= `llama-cpp-mine-v20dev`).
Runners in `validation/v20-scripts/`. Production units stopped the whole time, presets untouched.

## 1. The question: did the v17-v19 campaign slow Mistral / Qwen3.5-122B?

Code audit of every campaign commit (three reviews: flash attention, mat-vec / MoE, graph / host / multi-GPU) found
no change that targets these models, but several default-on paths they can reach, each with an env switch
(the list is in the plan file and in section 5). Measured with `llama-server`, each model's production rung near 65k,
two ~32k-token prompts + 2,048 generated tokens, greedy:

| model / rung | v16 | v19 | v19, campaign switches off |
|---|---|---|---|
| Mistral-Medium-3.5-128B :L (dense, TP, EAGLE) | pp 263/242, tg 7.3/6.9 | **pp 293/305, tg 9.6/9.7** | pp 270/265, tg 7.0/7.3 |
| Qwen3.5-122B :XS (MoE, TP, host KV, MTP) | aborts on request 1 | request 1 ok, **segfault on request 2** | ok, pp 157/284, tg 21/22 |

- Mistral-Medium is faster on v19 (+16% prefill, +37% decode); the campaign changes are what makes it faster.
- Qwen3.5-122B :XS cannot run on v16 at all (`SPLIT_AXIS_UNKNOWN` assert with host KV cells under `-sm tensor`,
  fixed in the campaign by fe49693b0) and crashes on v19 (section 4, fixed in v20).
- Qwen3.5-122B's speed problem is its placement, not a kernel regression: with every expert on the CPU
  (`--cpu-moe` + moe-hybrid) the GPUs are idle 91% of prefill and ~2/3 of decode (section 3).
- Mistral-Small-4-119B was not measured (stopped by the user).

## 2. The expert cache (`--moe-cache-slots N`, off by default) — approved by the user 2026-10-10

R9V's `cache80/192_prepare.cu` on our tiered tables (`moe-tiered.cu`). Per layer and device, N VRAM slots hold copies
of cold experts (the cold copy stays the home). Before a layer's first expert matmul of a decode or verify step
(<= 256 routes; mmvq and mmq): a one-block planner stamps the routed cached slots, picks the most routed uncached cold
expert and the least recently used slot not routed in this step; a fill kernel copies that expert for gate/up/down and
its last block publishes the table entries. GPU only, fixed pointers, graphs stay valid. With 0 slots: the layout and
the launches are unchanged.

Correctness: `test-moe-tiered` 105/105 with 0 and 4 slots; every Flash-Next text md5 e78f5272 (v19, v20 off, 16 and 32
slots); every Qwen3.5-122B text identical across arms.

Flash-Next (r9v-like tiered args, ub 1024, 65k, 32k prompt), ms per speculative step:

| arm | runs |
|---|---|
| v19 | 48.7, 85.9 (box noise, section 6) |
| v20, cache off | 48.5, 48.5, 48.7 (s5) |
| v20, 16 slots | 60.0 (noise), 40.3 |
| v20, 32 slots | 51.7 (noise), **37.9 (77 t/s)**, **37.6 (77.6 t/s)** (s5, after the meta fix) |

Quiet runs: 32 slots 37.9 and 37.6 ms/step (prefill ~1,480 t/s) vs 48.5-48.7 off (R9V: 41): -22%. Cache stats (16 slots, layer 47): hot 92.5% of routes, cache hits
5.5%, cold 2.0%, 0.45 fills per step. Needs a repeat on a quiet box before calling the size.

## 4. The v19 segfault on Qwen3.5-122B :XS — found and fixed

gdb (`s3-crash-bt.sh`, 2,048-token answers; with 512 it did not crash): thousands of nested
`ggml_backend_meta_get_split_state` frames, a stack overflow. The split state of a tensor recursed through its srcs
as deep as the graph. Fix (67c09e786): past depth 32 the srcs not answered yet are evaluated bottom-up with an explicit
stack, so the recursion stays shallow; same results. Verified (`s5.sh`): the exact crashing scenario (v20dev, :XS args,
defaults, two 32k prompts with 2,048-token answers) completes; Flash-Next texts unchanged (e78f5272).

## 6. Measurement noise on the rig

The same v19 binary ran 48.7 then 85.9 ms/step (prefill 1,363 -> 837) in one session; Qwen3.5-122B's no-cache arm
89.8 then 161.7. A bursty 32-worker torch job (`bench.tf.ppo`, nice 10, load average 20-33) ran throughout.
Hypothesis: `nice` shares CPU time, not DRAM bandwidth, and every cold expert is read by the GPUs from host DRAM over
PCIe, so the bursts slow exactly the tiered paths. Test (the user's call): pause the job (`kill -STOP` / `-CONT`)
for one interleaved A/B. Until then: interleave arms, repeat them, log `/proc/loadavg` per run (s4 does).

## 7. Decisions for the user

1. Cache size per Flash-Next rung (slots come out of the hot-set VRAM): 16 vs 32 slots, measured on a quiet box.
2. Qwen3.5-122B: move its DUALGPU rungs to tiered experts (hot set file + `-ot ...=ROCm0_TIERED` + cache slots);
   v20 build only. Load time (200-555 s) to fix first or accept.
3. Whether to pause the side job during A/B measurements.

## 8. Worklist

- Flash-Next dense verify (study of R9V, 2026-10-10): the real dense gap is ~1.5-2 ms/step, not 8.3 vs 3.9 (that
  compared different sets of kernels). Bit-identical: one launch for mat-vecs sharing an input (~0.4 ms). Text-changing:
  split the shared expert across GPUs like dsv4 (~0.3 ms), fuse HC-up + mix like R9V's hc_mixmmq45 (~0.5-0.8 ms).
- Tiered loader speed (keep mmap). `s6-loadprof.sh` (gdb samples, 302 s load): the server mostly waits: ~2/3 of the busy
  samples copy out of the mmap'd file (page faults; page cache fell 68 -> 27 GB during the load), ~1/4 pin the 37 GB
  cold block. A read-ahead of each tiered set_tensor's source range (`GGML_CUDA_TIERED_PREFETCH=1`, opt-in) gave
  on 286 / 210 s vs off 185 / 596 s: the box's page cache state dominates; inconclusive until a quiet box.
- Qwen3.5-122B ladder on tiered + cache, once the user decides (2).

## 9. Qwen3.5-122B ladder retuned on v20 (2026-10-10, with the user; config store commit 3c9a9a1)

The ladder rule, tiered experts + the expert cache, MTP n-max 4, 1/4 of the slot's context as host KV. Measured with
`s8-rung.sh` (prompt caching on, a random first word per request `BENCH_NONCE=1`, the preset's sampling, a 32k prompt,
2,048 tokens); the router's spawned args checked against the measured ones with `s9-router-args.sh` (identical but for
router-level flags).

| rung | slots x ctx | host KV/slot | hot set | peak/card | prefill | decode |
|---|---|---|---|---|---|---|
| (untagged), :XL | 1 x 262144 | 65536 | 44 GiB | 32.03 GB | ~1,080 | ~32 t/s (73 ms/step) |
| :M | 2 x 131072 | 32768 | 42 GiB | 31.83 GB | ~1,050 | ~26 t/s (noisy) |
| :S | 4 x 65536 | 16384 | 40 GiB | 31.43 GB | ~880 | ~26 t/s (noisy) |
| :XS | 8 x 32768 | 8192 | 38 GiB | 31.78 GB | ~900 | ~26 t/s (re-measure with a ~16k prompt) |

- Each slot keeps 1 + `spec-draft-n-max` copies of the delta-net state: n-max 12 cost ~0.95 GB per slot per card (the
  first :M/:S/:XS attempts ran out of memory at load). n-max 4 gives the same tokens per step (2.3-2.4) at ~0.36 GB.
- The 1 s sampler misses the runtime peak by 1-1.6 GB: a :M at 44 GiB sampled 32.6 GB and ran out of memory during the
  prefill; :XS at 40 GiB sampled 32.62 GB, so it ships at 38 GiB. Headroom target ~1 GB: tune later with the context.
- During a tiered load the server held 117.8 of 120 GB RAM (77 GB mapped file pages + 41 GB pinned cold experts):
  the likely cause of the slow, erratic loads (left for after the PPO job, the user's call).
- The rungs need the v20 build (`moe-cache-slots`; host KV under `-sm tensor` crashed v19). The production units still
  point at llama-cpp-mine-v19dev.
