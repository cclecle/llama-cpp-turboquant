# Playbook: tuning a model rung (preset) on the 2x R9700 rig

How the Qwen3.8-Flash-Next ladder was retuned on the v19 build (2026-09-27), written so the next ladder goes the same
way. The worked example is at the end.

## 1. Define the rung before tuning it

- **Context and slots first.** A rung is a total context (`c`) and a slot count (`np`). With `--no-kv-unified` each
  slot gets `c / np` cells.
- **Host KV headroom next.** Keep about a quarter of the context "ahead" in host RAM (`n-cpu-kv-cells`, per slot) so
  a long generation never overflows and a rung switch is smooth. It costs a little VRAM, so it goes in **before** any
  spare VRAM is spent. Exception: `-nckvc` is refused for models whose memory type cannot carry it (qwen4exp:
  `llama_memory_hybrid_idx`), and the rung then has no headroom.
- **The margin:** at least 1 GB free per card at the measured peak; below that is dangerous; never below 750 MB.

## 2. Measure like a client

A rung is only as good as the measurement behind it. Every one of these hid a real cost once:

- **Prompt caching on** (`BENCH_CACHE_PROMPT=1`). Clients use it, and it turns on context checkpoints. With
  `checkpoint-min-step 1024` below the rung's ubatch (1408), a checkpoint was saved every ubatch; for a hybrid
  recurrent model that copies large state to host RAM, and production prefill ran 3x slower than a benchmark sent with
  `cache_prompt: false`. Keep `checkpoint-min-step` at or above the ubatch (ideally the batch size).
- **The preset's sampling** (`BENCH_SERVER_SAMPLING=1`), not temperature 0: sampling lowers draft acceptance, so the
  best MTP depth can differ (Flash-Next: n-max 3 is +6% over 2 at temperature 0, a tie at 0.6).
- **Several runs per arm** when sampling (`BENCH_RUNS=4`): one sampled run is noise at the 5% level.
- **The full `[*]` block of main.ini**: a hand-rolled command line must carry every global key.
- **A full run, not a load-only peak.** The runtime peak exceeded the load-only peak by 0.6-1.2 GB at large contexts.
- **Vision rungs with an image request** (`FN_IMAGE=1`): a text benchmark never runs the encoder.
- When production disagrees with the benchmark, compare the **request** too, not only the command line and env.

## 3. Spend the VRAM

For a MoE with tiered experts the two levers compete for the same memory:

- **The hot set** (`moe-hot-experts`, generated by `scripts/fleet/moe_hotset.py --budget-gib G`) buys decode: every
  cold expert is read over PCIe.
- **The ubatch** buys prefill: the cold experts are re-read once per ubatch, so a larger ubatch reads them less often.

Measured slopes (Flash-Next, per card):

- A context doubling costs about 1.3 GB of KV per 64k tokens, and the QSA prefill buffers grow with context x ubatch.
- ubatch costs about 2 GB per 1024 tokens at 128k, 2.5 GB at 196k, and 0.8 GB per 256 tokens at 262k (ub 2048 does
  not even load at 262k).
- **More slots at the same total context cost less VRAM**: the attention buffers are sized per slot (2 x 131k used
  1.4 GB less than 1 x 262k).
- A hot set GiB is split over the two cards: 1 GiB total = 0.5 GB per card.

Method: from the previous rung's settings, shrink the ubatch first where it is expensive (large contexts) and the hot
set where the ubatch is cheap; confirm with a full run; spend the last few hundred MB on ubatch.

## 4. Speculative decoding

- Tune MTP depth after the VRAM, on the chosen config, at the preset's sampling.
- Compare **ms per step and tokens per step separately**: a changed text can raise tokens/s through acceptance while
  every step got slower.
- When the text changes, ms/step moves by about +-1 ms from the text alone: small decode differences need an
  identical text or pooled prompts.

## 5. Vision variants

- The mmproj and its encoder live on **card 0 only** (Flash-Next: +1.27 GB with a 1344x1344 image, 1,825 tokens;
  card 1 unchanged).
- The hot set and the ubatch shrink both cards, so cut them in proportion until card 0 has the margin; card 1 keeps
  the difference.

## 6. Record

- Write the measured peak, prefill and decode in a comment above each rung, and the build it needs.
- Keep hot-set files in the config store (`DUALGPU/hot/`), not in a bench folder.
- `/opt/llamacpp-config` is a git repo: one commit per rung (or per family).
